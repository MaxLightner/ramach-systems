# RAMACH Strategic Theses — v0.1

These are hypotheses to test, not final company definitions.

## Thesis 1 — RAMACH should be project-centered, not app-centered

A user should not experience Archiyar, Kamcheh, timeline, web, AI and future visualization as unrelated accounts and databases.

The project should be the durable object.

Potential project identity:
- owner / organization / permissions
- location / site / coordinate system
- design brief
- 2D/3D/BIM geometry and versions
- terrain / reality capture / context
- decisions and approvals
- timeline / reports / evidence
- tasks / issues
- people / roles / contractor history
- materials / products / suppliers
- quantities / cost / schedule
- public presentation layer
- AI history / generated alternatives / validation results

## Thesis 2 — Network should emerge from work, not precede it

Do not build “LinkedIn for construction.”

Potential valuable network edges:
- verified project ↔ verified contributor
- project ↔ contractor/team with actual execution history
- project ↔ supplier/product actually specified or installed
- owner ↔ architect/engineer selected for a real brief
- contractor ↔ workforce required for a specific work package
- completed project ↔ public portfolio/proof

If project records generate reputation automatically, the network gains trust data that generic social profiles lack.

## Thesis 3 — RAMACH's spatial advantage may be the initial wedge

Existing assets already touch:
- AR site visualization
- furniture/kitchen spatial planning
- Blender/web/mobile interoperability
- 3D/industrial real-time visualization

A credible near-term wedge may be:
**bring design into real spatial context, then keep that project context alive into execution.**

This needs market testing against simpler wedges such as procurement, project history, or contractor network.

## Thesis 4 — Premium visualization and scalable software are different businesses

VR cinematic experience, Gaussian Splatting site reconstruction and camera-tracked architectural films can be high-value project services before they become productized software.

Do not force every capability into SaaS.

Possible premium offer:
- capture real garden / mountain / urban site
- integrate proposed villa/building
- cinematic still/video
- VR walkthrough
- AR on-site review
- later connect same project to Archiyar/project identity

## Thesis 5 — AI should attach to structured project context

Avoid standalone “prompt → house” positioning.

Long-term ambition:
brief → site/rules → architecture → structure → MEP → coordination → quantities/cost → documentation.

Near-term implementation should start only where outputs can be tested and corrected.

## Thesis 6 — Iran may reward integration more than feature novelty

First-pass research shows local players in nearly every isolated category:
VR/AR, BIM, AI claims, project management, architecture communities, architect marketplaces, procurement and supplier networks.

Potential whitespace:
**one project record that carries context through design, visualization, execution, network and public proof.**

## Highest-priority research questions next

1. Who owns the project record in Iran: owner, architect, contractor, consultant or developer?
2. Which actor can introduce RAMACH into a project with the least sales friction?
3. Which project type should be the beachhead: luxury villas, custom residential, architecture firms, mid-size contractors, industrial projects?
4. What information are teams already willing to maintain digitally?
5. Which existing tools are unavoidable (Revit, AutoCAD, Excel, WhatsApp, Telegram) and therefore must be integrated rather than replaced?
6. What exact project artifact creates recurring usage after the initial “wow” of AR/VR?
7. Which data can become verified reputation for professionals?
8. Which workflows have the strongest willingness to pay in Iran?
9. What is the lowest-cost path to a real AI engineering benchmark?
10. What regulatory/legal constraints apply to engineering output and marketplace claims?
